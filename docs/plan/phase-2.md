  * The plan, as written before the work:
  * The method is WSOLA (waveform similarity overlap-add). The finished speech is cut into slices of about 20 to 30 ms, each long enough to hold a few repeats of the voice's wave, so each keeps the pitch. Only some slices are kept: for five times as fast, the kept slices are five times as far apart in the original as in the result. Each slice fades into the next. Before each join, the slice's start is nudged a little to where its wave best lines up with the end of the one before, so the joins are not rough or buzzy.
  * Piper first speaks as fast as it cleanly can, about twice as fast (length_scale 0.5). Time stretching then makes up the rest of the speed chosen. Below that speed, nothing changes from now.
  * Gaps between words are shortened first, as screen readers do at high speeds, so less of the words themselves has to be cut.
  * It goes in the core, as NumPy only (it must run in Pyodide, where NumPy is 32-bit: use np.intp for offsets), so the desktop and the web share it (AD-1). Probably a new module beside mapcore/sound/scene.py, called where each shell gets a label's samples from Piper.
  * Tests first: the result's length is the original's divided by the stretch, within a slice; the pitch is unchanged (a test tone keeps its frequency, measured by its zero crossings or an FFT); no clicks at the joins (no jump between samples beyond the tone's own).
  * Samples for the PO: the same sentence at 200, 300, 400 and 500 percent, as WAV files, so the PO judges whether 500 sounds too choppy. Five times can sound a little robotic, as more of each sound is dropped.
  * The same tool could lower the voice behind you without slowing it down: stretch longer first, then resample faster to bring the pitch down. Today the voice behind is tape-style resampled to about 0.84 (BEHIND_PITCH), which also slows it. Add that version to the voice-behind samples planned below, so the PO can compare.
